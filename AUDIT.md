## Коротко для Дамира

1. Текущая Платформа — это **площадка переводов** (заказ перевода → переводчик → проверка →
   нотариус → выдача). Она аккуратно доведена до демонстрации, но **всё в ней заточено под перевод**:
   заявка — это «языковая пара + страницы», исполнитель — «переводчик с языками», статусы —
   «проверка перевода, заверение у нотариуса».
2. Три «готовые части», на которые рассчитывал устав, на деле **не готовы**:
   - **вход** — есть, но код подтверждения всегда «0000», СМС не отправляются;
   - **оплата ЮKassa** — не подключена вовсе: кнопка «оплатить» только ставит отметку в базе.
     Готовы лишь страницы для анкеты ЮKassa (оферта, цены, реквизиты);
   - **уведомления** — есть пустая таблица, ни одно уведомление не отправляется.
3. В коде есть **серьёзные дыры доступа**: войти можно под любым номером (в том числе
   администратора), любой вошедший видит и меняет чужие заявки. С реальными людьми
   в таком виде запускать нельзя.
4. bertel.online сейчас **не работает** (в облаке остановлен входной шлюз, по данным от 20.09).
5. **Рекомендация: новый репозиторий с переносом готовых частей.** Под «любые услуги»
   придётся переписать больше половины кода — заявку, исполнителя, оплату и все кабинеты.
   Переносим то, что действительно работает: выкладку в Яндекс Облако, хранение файлов,
   схему входа по телефону, переписку по каналам, модель денег 80/20, правовые страницы.
   Сроки — в разделе 9.

## 2. Где и как работает

- **Хостинг:** Yandex Cloud, каталог `b1ghui999c328vf1j841`. Статика — бакет `bertel.online`;
  сервер — Serverless Container (128 МБ, 1 одновременный запрос, 10 с на запрос);
  вход — API Gateway. Файлы — бакет `bertel-files`. База — через переменную `DATABASE_URL`

  контейнера). Проверочного стенда нет. Это противоречит правилу устава «боевой релиз двигает только Дамир».
- **Секреты:** строка подключения к базе и ключи хранилища передаются контейнеру
  **открытыми переменными окружения** из секретов GitHub (видны в консоли облака в описании ревизии).
- **В публичный бакет выгружается весь корень репозитория**, кроме нескольких исключений:
  прототипы, `test.html`, `konsol.html`, а после этого аудита — и все `.md`-файлы проекта
  (устав, аудит) стали бы доступны из интернета. Исправлено в этой ветке: `deploy.yml`
  теперь исключает `*.md`, `tests/`, `infra/`, служебные файлы.
- **Состояние на 20.09.2026:** шлюз остановлен, bertel.online отдаёт 503. Из этой среды
  облако Яндекса недоступно (сетевые ограничения среды), поэтому живую проверку сделать нельзя.
- **Старая копия на Netlify** (`bertel-platforma.netlify.app`) — переадресация настроена в коде,
  но Netlify не публикует новые версии. База Neon (США) и Netlify Blobs (США), по старому

## 3. Что работает (проверено автотестами на локальной базе)

Проверено в этой сессии на чистой базе PostgreSQL 16 (см. раздел 8):

- создание схемы и демо-данных с нуля;
- вход по телефону (демо-код), регистрация нового заказчика/переводчика, лимит 5 неверных попыток;
- запрет регистрации сразу администратором/диспетчером;
- проверка ролей на уровне операций (401 без входа, 403 для чужой роли);
- **полный путь заявки перевода**: создание → оплата (отметка) → автоподбор переводчика →
  принятие → проверка качества → выбор нотариуса → заверение → приёмка заказчиком →
  выплата исполнителю с комиссией 20%;
- защита переходов статусов (недопустимый переход — 409), роль берётся из сессии;
- автоподбор учитывает подтверждённую языковую пару, загрузку и рейтинг;
- файлы: загрузка до 5 МБ, скачивание только участником заявки, удаление владельцем;
- переписка по каналам: заказчик не видит служебный канал «переводчик — проверка»;
- публичные страницы и 6 кабинетов открываются на телефоне 412×915 (результаты — раздел 8).

## 5. Безопасность (найдено, подтверждено тестами)

Автотесты `tests/api/known-gaps.test.mjs` и `tests/ui/phone.spec.mjs` воспроизводят каждую дыру
(помечены как «известная проблема», чтобы не валить прогон; после исправления пометка снимается).

| № | Дыра | Последствие |
|---|---|---|
| Б-1 | Код входа всегда «0000» | Любой входит под любым номером, **включая администратора** (номера демо-учёток лежат в коде) |
| Б-2 | `op=order` отдаёт любую заявку любому вошедшему | Чужие заявки видны (нарушение «чужие дела не видны никому») |
| Б-3 | `op=list` — список всех заявок любому вошедшему | То же |
| Б-4 | `op=action` не проверяет, что заказчик — владелец заявки | Чужой заказчик может отменить/«оплатить»/принять чужую заявку |
| Б-5 | То же для исполнителя | Любой переводчик принимает заявку, предложенную другому |
| Б-6 | `dbinit`, `migrate`, `ensure_chat`, `ensure_refs` доступны без входа | Любой из интернета запускает изменения схемы базы |
| Б-7 | Имена пользователей выводятся в кабинетах без экранирования | Зарегистрировавшись с «именем»-скриптом, можно украсть сеанс администратора, когда он откроет список пользователей |
| Б-8 | Координатор/руководитель **любого** бюро имеет доступ к файлам **любой** заявки | Утечка между организациями |
| Б-9 | Токен сеанса передаётся в адресе при скачивании файла и хранится в `localStorage` | Попадает в журналы и историю браузера; уязвим при Б-7 |
| Б-10 | Если у пользователя нет своей записи заказчика/переводчика, код подставляет **демо-учётку** (`+79990000001`, `+79990000010`) | Заявки/данные молча приписываются чужому аккаунту |
| Б-11 | Ошибки сервера отдаются клиенту текстом исключения; ошибки входа — со статусом 200 | Утечка деталей базы, путаница в клиенте |
| Б-12 | Секреты — открытыми переменными окружения контейнера | Видны всем, у кого есть доступ к консоли облака |
| Б-13 | Подключение к базе без сертификата молча переходит в режим «не проверять SSL» | Возможен перехват соединения |

## 7. Можно ли обобщить заявку, исполнителя и оплату (критерий устава)

Оценка по серверу (`api.mjs`, 1004 строки) и кабинетам:

- **Заявка.** Таблица `orders` и тип `order_status` целиком под перевод; 14 переходов
  (`TRANSITIONS`) — это процесс перевода с нотариусом. Для ядра нужны другие поля, другие статусы
  и описание процесса как данных модуля. → **переписать.**
- **Исполнитель.** `translators`, `translator_languages`, `bureau_members`, подбор по языковой паре,
  отказ «с последствиями» — всё про переводчиков. Для ядра нужен «специалист» с профессией,
  допусками, специализациями, районом работы. → **переписать** (идея верификации с журналом
  событий `verification_events` переносится).
- **Оплата.** Реальной оплаты нет; есть расчёт 80/20 и таблицы `payments/payouts/payout_splits`.
  ЮKassa (агентская схема, чеки, выплаты) пишется с нуля в любом случае. → **писать заново**,
  таблицы — как образец.
- **Кабинеты.** Все 6 под перевод, с копиями кода и без экранирования. Устав задаёт новый образец
  кабинетов (проблема → ИИ → специалист → дело). → **переписать.**
- **Безопасность доступа.** Проверки владельца нужно вшить в каждую операцию → затрагивает
  почти все функции `api.mjs`.

Грубо по объёму: из ≈ 5 100 строк рабочего кода (сервер + кабинеты + вход) переносится как есть
или с малой правкой ≈ 700–900 строк (обёртки базы и хранилища, запуск сервера, вход по телефону,
файлы, переписка по каналам, правовые страницы), **остальные ≈ 80–85% переписываются.**
Порог устава («больше половины») превышен.

## 9. Два пути и сроки

Сроки — в рабочих сессиях Claude Code (одна сессия ≈ один полный контекст), при ответах Дамира
в течение дня. Этап 0 (контур в РФ, тесты, решение) в обоих путях одинаков: **1–2 сессии**
после получения доступа к облаку.

### Путь А — строить ядро на этой основе
Придётся переделать: схему заявки и статусов, исполнителя и подбор, оплату (с нуля), все 6 кабинетов,
проверки доступа во всех операциях, миграции схемы, разделение ядра и модуля перевода — **внутри
работающего кода с демо-данными перевода**, сохраняя его рабочим (иначе теряется смысл пути А).
- Этап 1 (ядро): **14–18 сессий**.
- Риски: переводческая логика «протекает» в ядро; двойная работа — сначала обобщить старое, потом
  строить новое; старые дыры доступа легко пропустить в одной из 70 операций; история репозитория
  и выкладка остаются привязаны к старому сайту.

### Путь Б — новый репозиторий с переносом готовых частей (рекомендуется)
Переносим: выкладку в Яндекс Облако (контейнер + шлюз + бакет, с исправлениями из раздела 5),
обёртку хранилища файлов, подключение к базе, вход по телефону (логику кодов и попыток; СМС —
новое), переписку по каналам заказа и блок файлов, модель денег 80/20 и таблицы оплат как образец,
журнал статусов и верификаций, правовые страницы (оферту — переписать под агентскую схему БЕРТЕЛ Дело).
Строим заново: заявку, специалиста, организацию, подбор, кабинеты по образцу 1а, проверки доступа
с первого дня, миграции схемы, проверочный и боевой стенды.
- Этап 1 (ядро): **11–14 сессий**.
- Модуль перевода (этап 2а) позже собирается на новом ядре; текущий код остаётся образцом
  процесса перевода и не удаляется.
- Риски: несколько сессий нет ничего «показать» — снимается тем, что проверочный стенд
  поднимается в первой же сессии этапа 1.

### Почему Б
1. Порог устава превышен (≈ 80–85% переписывается).
2. «Готовые части» из устава фактически не готовы — переносить почти нечего, а то, что переносим,
   небольшое и хорошо отделяется.
3. Проверки доступа, миграции и тесты проще заложить с первого дня, чем вшивать в 1000 строк.
4. Чистое разделение: старый сайт перевода и его выкладка не мешают ядру; боевая выкладка
   нового ядра — только по решению Дамира.

## 10. План развёртывания базы и хранилища в Яндекс Облаке с нуля

Подробный план и готовая конфигурация — `infra/README.md` и `infra/terraform/`. Кратко:

- **Два каталога** в облаке: «проверочный» (`delo-stage`) и «боевой» (`delo-prod`),
  одинаковая конфигурация. Всё в зоне `ru-central1` (Россия).
- **База:** Yandex Managed PostgreSQL 16; защита от удаления; ежедневная автоматическая копия
  с хранением 14 дней (стенд) / 30 дней (бой) и восстановлением на любой момент;
  дополнительно — еженедельная выгрузка базы в отдельный бакет копий с защитой от удаления.
  Доступ к базе — только из облачной сети и только по SSL с проверкой сертификата.
- **Файлы:** Yandex Object Storage, закрытый бакет, шифрование ключом KMS, хранение версий
  (удалённое можно вернуть 30 дней), выдача файлов — только временными ссылками после проверки прав.
- **Секреты:** Yandex Lockbox; контейнер получает их из Lockbox, в GitHub хранится только ключ
  для выкладки.
- **Выкладка:** проверочный стенд — автоматически после слияния в `main`; боевой — только
  ручным запуском, который делает Дамир (или по его прямому «да»).
- **Ориентировочная стоимость** (уточняется в калькуляторе Яндекса перед созданием; решение о
  платеже — за Дамиром): стенд ≈ 3–5 тыс. ₽/мес, бой на старте ≈ 10–15 тыс. ₽/мес.
- **Что нужно от Дамира один раз:** доступ к облаку (см. «Решить Дамиру» в `STATE.md`).
