## 1. Что строим

Единая цифровая платформа, где клиент решает свой вопрос с помощью ИИ и специалистов:
адвокаты/юристы, эксперты (сначала оценщики, затем другие виды экспертиз), переводчики
с нотариальным заверением, арбитражные управляющие (в будущем) и другие смежные профессии.
Платформа ещё не запущена, живых пользователей и заказов на ней нет — ядро строится
сразу под первый продукт.
Клиенты: частные лица и юридические лица (в том числе банки, лизинговые и страховые
компании, юрфирмы). Госорганы (следствие, суды) обслуживаются через БЕРТЕЛ CRM, а не здесь.

Принцип «одно ядро — разные модули»:
- **Ядро** — общее для всех: учётные записи и организации, заявки, подбор исполнителя,
  документы и подписи, оплата, уведомления, ИИ-помощники, API наружу.
- **Модули** — профессии/виды услуг: экспертиза и оценка, перевод и нотариат, юристы;
  далее арбитражные управляющие и другие по образцу раздела 1а.
- **Кабинеты** — разные входы в одно ядро: клиент (физлицо / юрлицо), специалист,
  диспетчер, администратор.

Не строим три отдельные платформы. БЕРТЕЛ CRM (бертел.рф) остаётся отдельной закрытой
системой для госзаказа и в ядро не сливается. Госорганы к Платформе не подключаются,
внешнего API у CRM нет.

**Связь CRM и Платформы для исполнителей** — только через внутренний мост, в одну
сторону (CRM → Платформа), без персональных данных и материалов дел:
- один вход и один профиль исполнителя (языки, квалификация, документы, рейтинг).
  Порядок: CRM запускается первой со своими профилями; на этапе 1 профили один раз
  автоматически переносятся в ядро Платформы, после чего CRM переходит на общий вход
  и свой профиль отключает. Для переезда в CRM нужны уникальные телефон и почта,
  языки и квалификация — структурированными полями, а согласие на обработку
  персональных данных — с упоминанием Платформы как сервиса той же группы;
- один список предложений: из CRM приходит только «госзаказчик, язык, срок, объём,
  оплата по ПП №1240» — без номера дела и фамилий; принял — работает внутри CRM;
- одна загрузка: CRM передаёт Платформе только число текущих дел исполнителя,
  чтобы автоподбор его не перегружал.
Базы не сливаются, выплаты раздельные (госзаказ — как сейчас, Платформа — ЮKassa),
в общем кабинете исполнитель видит оба списка.

Образец по функциям — Reggora (США): автоподбор исполнителя, статусы без звонков,
проверка результата до выдачи, оплата и выплаты внутри системы, экспресс-услуга
с дистанционным осмотром, бесплатный кабинет исполнителя, API для крупных заказчиков.

## 1а. Видение и образец кабинета

Смысл платформы: человек приходит с проблемой, а не за услугой, и уходит с решённым вопросом.
ИИ разбирается в ситуации, подсказывает путь, подключает специалиста из системы; дело ведётся
и отслеживается в одном месте с проверкой качества на каждом шаге.

Все кабинеты строятся по одному образцу — это и есть причина одного ядра.

**Кабинет специалиста** (адвокат/юрист, эксперт, переводчик, арбитражный управляющий и любая
следующая профессия): поток заявок и клиентов → работа над делом в электронном виде →
ИИ-проверка результата перед отправкой заказчику по списку правил этой профессии
(оценщик — погрешности, расчёт, реквизиты и технические ошибки отчёта; переводчик — полнота
и точность перевода, термины, оформление; юрист — соответствие документов действующему
законодательству, ссылки на нормы, сроки) →
личный ИИ-ассистент по делам (расширение на повседневную жизнь — по желанию, отдельное
согласие, отдельная память).

**Кабинет клиента** (частное или юридическое лицо): описал проблему → ИИ разобрался
и объяснил, какие есть пути → предложил, что сделать самому и к кому обратиться →
подключил специалиста из системы → дело ведётся в электронном виде и отслеживается
автоматически (статусы обновляются сами, напоминания о сроках), клиент видит каждый шаг.

**Кабинет организации** (адвокатское бюро, коллегия, юрфирма, экспертная организация,
бюро переводов, юротдел компании, отдел банка): руководитель или старший партнёр видит дела
всех сотрудников, распределяет заявки, контролирует сроки и качество, видит нагрузку и деньги
по организации. Сотрудник видит только свои дела. Это третий слой образца, общий для всех
профессий: удобный ежедневный инструмент для организации — главная причина, по которой
её сотрудники заказывают экспертов и переводчиков у нас, одной кнопкой изнутри дела.
Не повторяем целиком существующие системы ведения дел (учёт времени, счета, бухгалтерия);
отличаемся ИИ-помощником в деле, проверкой документов и специалистами в один клик.

**Новая профессия = три описания, а не новый кабинет:** перечень услуг, поля заявки,
список ИИ-проверок. Кандидаты на будущее: нотариусы, кадастровые инженеры, патентные
поверенные, аудиторы и бухгалтеры, таможенные брокеры, страховые агенты, риелторы,
медиаторы, специалисты по банкротству физлиц; сотрудники банков, лизинговых и страховых
компаний — как заказчики.

Незыблемые правила:
- ИИ-консультация клиента — разъяснение, не юридическая услуга; всегда заканчивается
  «что сделать самому» или «вот специалист».
- Каждая ИИ-проверка — помощь специалисту, не замена; подпись и ответственность у человека.
- Личное и рабочее у одного пользователя не смешиваются; чужие дела не видны никому.

Первый продукт (экспертиза) строится как первый экземпляр этого образца: уже в нём есть
кабинет клиента с ИИ-разбором проблемы, кабинет эксперта с ИИ-проверкой отчёта и ассистент.

## 2. На чём строим

- Отправная точка — существующий репозиторий `damvaf6/bertel_platforma` (bertel.online):
  в нём есть готовые части (вход, оплата ЮKassa, уведомления). Строить ядро в нём или в новом
  репозитории с переносом этих частей — решает аудит этапа 0 и Дамир.
- Хостинг — Yandex Cloud (уже используется).
- **Данные только в России (152-ФЗ).** Нынешние база Neon Postgres и хранилище Netlify Blobs
  находятся за рубежом и в боевом контуре не используются. Этап 0 разворачивает базу
  в Yandex Managed PostgreSQL (или Selectel) и файлы в Yandex Object Storage с нуля;
  переносить нечего. Реальные персональные данные — только в российский контур.
- ИИ — модель как настройка, переключаемая без переделки кода.
  Старт: YandexGPT Pro (Yandex Cloud AI Studio, OpenAI-совместимый API).
  Запасная: GigaChat. Зарубежные модели в контуре с персональными данными не использовать.
- Оплата — ЮKassa, агентская модель, комиссия платформы 20% (уже заложено).
- Подпись заключений и документов — УКЭП исполнителя (интеграция — отдельная задача этапа 2).

## 3. Порядок работ

### Этап 0 — Аудит и фундамент
- Полный аудит текущей Платформы: что есть, что работает, что нет. Результат — `AUDIT.md`.
  Аудит обязательно заканчивается рекомендацией: **«строить ядро на этой основе»** или
  **«новый репозиторий с переносом готовых частей (вход, оплата, уведомления)»** — с причинами,
  списком того, что придётся переделать, и оценкой сроков для обоих путей.
  Критерий: если заявку, исполнителя и оплату нельзя обобщить под любые услуги без переписывания
  больше половины кода — рекомендовать новый репозиторий. Окончательное решение принимает Дамир;
  до него этап 1 не начинается.
- Развёртывание базы и хранилища файлов в РФ с нуля; резервное копирование настроено сразу.
- Автотесты и проверка интерфейса на телефоне (Playwright, 412×915) как обязательная
  часть каждого выпуска.
- `CLAUDE.md`, `STATE.md`, `DECISIONS.md`, `TASKS.md` заведены и заполнены.

**Готово, когда:** контур в РФ развёрнут, тесты зелёные, принято решение об основе ядра.
*Исключение (решение Дамира 30.09.2026):* этап 1 начинается до развёртывания контура в РФ, только на тестовых
данных; контур разворачивается до первого показа, настоящих данных до этого нет. Как проверяется работа
без облака — `DECISIONS.md`, 30.09.2026.

### Этап 1 — Ядро
- Организации и роли (заказчик / исполнитель / диспетчер / администратор), один вход.
- Слой «организация»: руководитель и сотрудник, видимость дел внутри организации,
  распределение заявок руководителем, контроль сроков и нагрузки по сотрудникам.
  Нужен сразу — для ЦНЭР и бюро переводов как исполнителей.
- Единая «Заявка»: тип услуги, объект, срок, основание (постановление / договор),
  статусы: новая → подбор → ждёт исполнителя → в работе → проверка → готово → закрыто.
- Автоподбор исполнителя: специализация и допуск (обязательно), расстояние, загрузка,
  срок, качество прошлых работ. Диспетчер видит оценку по признакам и может переназначить.
- Заявка по письму: специальный адрес, письмо с вложениями → ИИ разбирает и создаёт заявку,
  отвечает номером; готовый результат уходит ответом в ту же переписку. Способ подключить
  юрфирмы и компании без переезда из их систем. Позже — кнопка-ссылка с подстановкой данных
  из карточки дела; полное API — этап 4.
- Вход через проблему: клиент описывает вопрос своими словами → ИИ разъясняет ситуацию,
  предлагает, что сделать самому и к какому специалисту обратиться → создаёт заявку.
- Кабинет клиента: дело со статусом по этапам, документы, оплата онлайн; автоматическое
  отслеживание — статусы и напоминания о сроках без участия диспетчера.
- Кабинет специалиста: предложения (принять/отказаться), работа над делом, ИИ-проверка
  перед сдачей, сдача, выплаты, поток клиентов.
- Кабинет диспетчера: все заявки, подбор, проверка, деньги.
- Проверка результата до выдачи: список правил + ИИ-проверка, человек смотрит отмеченное.
- Уведомления: единый реестр типов, настройки у пользователя (по образцу CRM).
- Деньги: получено / к выплате / комиссия, автовыплата после выдачи и оплаты,
  закрывающие документы.
- Личный ИИ-ассистент по делам в кабинете специалиста и клиента через переключаемую модель.
  Память ассистента — раздельная по организациям и пользователям; чужие данные никогда
  не смешиваются. Расширение на повседневную жизнь — по желанию пользователя, отдельное
  согласие и отдельная память (не раньше этапа 3).
- Мост CRM → Платформа (см. раздел 1): единый вход и профиль исполнителя, короткие
  предложения из CRM без данных дела, передача числа текущих дел для автоподбора.
  Изменения на стороне CRM — отдельными задачами в проекте CRM, после релиза ядра.

**Готово, когда:** тестовая заявка на экспертизу проходит весь путь целиком на телефоне
без участия разработчика, все тесты зелёные.

### Этап 2 — Модуль «Экспертиза и оценка» (первый продукт)
- Виды на старте: оценка недвижимости, земли, транспорта, движимого имущества, товароведческая.
  Другие виды экспертиз (строительно-техническая, почерковедческая и т.д.) подключаются позже
  по образцу раздела 1а: перечень услуг, поля заявки, список ИИ-проверок.
- ИИ-проверка отчёта перед отправкой клиенту: реквизиты, расчёт, аналоги, погрешности,
  технические ошибки; эксперт видит отмеченные места и подписывает.
- Черновик заключения от ИИ по данным заявки и фото → эксперт правит и подписывает.
- Дистанционный осмотр: ссылка владельцу, пошаговая фотофиксация с геометкой.
- Экспресс-услуга: сбор данных помощником на объекте, эксперт дистанционно.
- Подпись УКЭП, выдача заключения в кабинет.
- Первые исполнители — АНО «ЦНЭР» и её эксперты на общих условиях.

### Этап 2а — Модуль «Переводы и нотариат»
- Добавляется после выхода экспертизы на реальные заявки: те же заявки, исполнители и оплата,
  свои поля (языки, заверение, нотариус). ИИ-проверка перевода перед отправкой: полнота,
  точность, термины, оформление. Первый исполнитель — ООО «АИС Переводчик».

### Этап 3 — Модуль «Юристы» и «Дело» частного лица
- Кабинет юриста/адвоката/арбитражного управляющего: дела, сроки, задачи, документы,
  ИИ-помощник в деле, заказ эксперта и переводчика одной кнопкой изнутри дела.
- Кабинет юридической организации (бюро, коллегия, юрфирма, юротдел): контроль руководителя
  и старших партнёров над делами сотрудников — по слою «организация» из этапа 1.
  Первая версия узкая: без учёта времени, счетов и бухгалтерии. Крупным фирмам со своей
  системой ведения дел — подключение через API (этап 4), без переезда.
- «Дело» частного лица: ИИ готовит документы и план, юрист проверяет, подписывает и ведёт.
- ИИ-проверка документов юриста перед отправкой: соответствие действующему законодательству,
  ссылки на нормы, сроки, реквизиты.
- Арбитражные управляющие — тем же образцом, после юристов.
- Подбор представителя с учётом ограничений: уголовные дела — только адвокат;
  гражданские и арбитражные — высшее юридическое образование (кроме мировых и районных судов).
- ИИ ничего не подаёт и не отправляет сам.

### Этап 4 — API наружу
- Только когда есть первый заказчик, которому это нужно (банк, страховая, лизинг).
- Создание заявки, статус, уведомление о готовности, передача файла. Ключи, лимиты, журнал.

Порядок этапов менять нельзя. Внутри этапа задачи ведутся в `TASKS.md`.

## 4. Правила работы сессий

1. **Начало сессии:** прочитать `CHARTER.md`, `STATE.md`, `TASKS.md`, `DECISIONS.md`. Продолжать с первой незакрытой задачи.
2. **Конец сессии (и перед исчерпанием контекста):** обновить `STATE.md` (сделано / не проверено / следующий шаг / последние коммиты). Вопросы Дамиру — только в раздел «Решить Дамиру» в `STATE.md`, одним списком, без переписки.
3. **Решения фиксируются** в `DECISIONS.md`: дата, что решено, почему, что отвергнуто.
4. **Проверка до доклада:** тесты запускаются автоматически; интерфейс проверяется Playwright на размере телефона со скриншотами. «По логике должно работать» — не принимается. Ни одна задача не закрывается без проверки на боевом адресе после выкладки.
5. **Выкладка:** push в `main` → автосборка. Боевой релиз двигает только Дамир, как в CRM. Ничего необратимого (удаление данных, смена схемы без резервной копии, платежи) без явного «да» Дамира.
6. **Ключи и пароли** — никогда в репозиторий, в память и в документы. Запрашивать у Дамира один раз в сессию, после использования он их отзывает.
7. **Дамира не грузить:** не присылать ход работы и промежуточные отчёты; не давать ему ручных проверок; объяснять без технических терминов. Одна сводка в конце сессии по его запросу.
8. **Первая версия — узкая.** Ничего сверх этапа не добавлять, даже если «просто и полезно». Идеи — в `IDEAS.md`.
9. **Данные:** тестовые данные помечены, реальные персональные данные — только после этапа 0 и политики по 152-ФЗ.
10. **Модель для сессий:** Opus. Fable 5.1 — только для отдельного архитектурного разбора по решению Дамира.
